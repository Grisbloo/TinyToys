# Tiny Toys Game Jam

A personal game-development challenge focused on **breadth, experimentation, and finishing things**.

The goal isn't to make impressive games.

The goal is to repeatedly go:

**Idea → Scope → Build → Debug → Finish → Ship**

Each game is intentionally small so that I can experiment with a new mechanic, concept, or programming problem without getting trapped in a giant project.

---

## The Rules

### 1. One Weekend

Each game gets one weekend.

The exact amount of time spent during the weekend doesn't matter. There are no hourly quotas.

The goal is simply:

> **Start it over the weekend. Finish it over the weekend.**

---

### 2. Monday Is Bug-Fixing Day

Monday is for fixing bugs.

**No new features.**

If something is broken, it can be fixed.

If I suddenly think:

> "Oh, it would be cool if I added..."

That's a new feature.

**Don't add it.**

---

### 3. One Core Mechanic

Every game must have a simple central idea.

Examples:

* Move a box around a board.
* Avoid incoming bullets.
* Drive a train through signals.
* Keep something from falling.
* Sort objects.
* Survive for 60 seconds.

The game can have supporting systems, but there should be one obvious answer to:

> **"What am I actually doing?"**

---

### 4. One Scene

The default scope is **one scene**.

The purpose is to prevent the project from turning into architecture homework.

If the game can exist in one scene, it should.

---

### 5. Simple Assets

Use primitives, simple shapes, basic materials, and whatever assets are immediately available.

No spending the entire weekend making a beautiful model for a game that exists primarily to teach me how collision detection works.

**The mechanic comes first.**

---

### 6. No AI-Written Code

The purpose of this challenge is to improve my ability to program **on the fly**.

AI can be used as:

* Documentation
* An explanation of an API
* A debugging partner
* A source of conceptual explanations
* A second pair of eyes

AI should **not write the implementation for me**.

If I need help, I should understand the solution rather than copy it.

---

### 7. Documentation Is Allowed

Looking things up is completely fair game.

Reading:

* Godot documentation
* API references
* Programming documentation
* Error messages
* Language references

is part of programming.

The restriction is against copying a complete solution and calling that learning.

---

### 8. No "While I'm Here..."

This is the most important rule.

If I find myself thinking:

> "While I'm here, I might as well add..."

**STOP.**

That thought is how a weekend project becomes a six-month project.

Write the idea down somewhere instead.

It can become:

* A future tiny game
* A future feature
* A future serious project

But it does not belong in the current game.

---

## The Depth Trap

I naturally tend to think about systems deeply.

That's useful for large projects, but it can make small projects impossible to finish.

For example, a simple tank game might immediately turn into questions about:

* Different missile seeker heads
* Sensor physics
* Light levels
* Guidance systems
* Vehicle electronics
* Historical accuracy
* Different ammunition types
* Damage models

Those are interesting questions.

They are also exactly how a "tiny toy" becomes a massive project.

The Tiny Game Jam deliberately prioritizes:

> **Breadth first. Depth later.**

I want to experience many different programming problems before attempting to solve each one in extreme depth.

---

## Graduation Rule

A tiny game is allowed to become a bigger project.

If an idea survives the tiny-game process and I genuinely want to explore it further, it can graduate into its own project.

The tiny game does **not** have to contain the complete version of the idea.

The tiny game only has to prove that the idea is interesting enough to continue.

---

## Definition of Finished

A game is finished when:

* The core mechanic works.
* The player can actually interact with it.
* The game can be started and played.
* Major bugs are fixed.
* The scope has stopped expanding.

It does **not** need:

* Perfect art
* Perfect sound
* Menus
* Achievements
* Settings
* Lore
* Multiplayer
* A monetization strategy
* A 40-page design document

**Finished beats impressive.**

---

## The Point

This challenge exists to practice something that is easy to neglect when working on a large project:

**Finishing.**

Every tiny game is another repetition of the process.

```text
Think of something
       ↓
Define the smallest possible version
       ↓
Build it
       ↓
Get stuck
       ↓
Figure it out
       ↓
Fix it
       ↓
Finish it
       ↓
Move on
```

The goal isn't to become an expert at every system.

The goal is to become comfortable encountering something I've never done before and thinking:

> **"Alright. Let's figure this out."**
